# Changelog

Sentry UA's decision log, oldest first. Every change gets an entry explaining *why* it was made, not just what changed - including approaches that were tried and reverted, and known limitations that were accepted deliberately. Entries from before 2026-09-24 weren't dated individually.

For how to install and use the current version, see [README.md](README.md).

### Dialog persistence, grid selection, and chart-as-filter fixes
- Reverted the earlier "pause autorefresh while the dialog is open" approach. It ran into a genuine race condition: the previous autorefresh timer is a client-side JS interval that can't be cancelled the instant a dialog opens, so an already-in-flight tick could still sneak through right after opening, and the app had no reliable way to tell that stray tick apart from the user actually closing the dialog. Symptoms were a dialog that flickered shut immediately on the very first click, and one that occasionally swapped to a different UA a moment after opening. Autorefresh now runs continuously and unconditionally again.
- Both AG Grid and the Vega-Lite chart persist their own selection state across reruns, tied to their widget keys, entirely independent of `st.session_state`. The code that reads each one now only adopts a selection when it's genuinely different from what was last observed for that widget - previously it would unconditionally re-derive `selected_ua`/`chart_ua` from whatever each widget still reported as selected on every single run, which both reopened the dialog right after Reset (each widget still "remembered" its old selection) and could clobber a fresher selection something else had just set. Reset also now gives both widgets a fresh key (via a bumped nonce), so they start genuinely unselected rather than relying only on the tracking check.
- Streamlit gives no callback for "the user dismissed this dialog" - by default, dismissing via the X, Escape, or clicking outside doesn't even trigger a rerun, so Python never directly learns it happened. Reopening is inferred instead: the autorefresh timer's own return value is captured each run to know whether *this* rerun was a routine data refresh. If the same selection comes up again on a rerun that *wasn't* an autorefresh tick, that can only mean some other real interaction occurred (Reset, a filter tile, or the dismissal itself) - and since the dialog is a true modal blocking everything behind it, reaching any other interaction means it must already have been dismissed. That gets remembered per-selection so it stays closed on every later autorefresh tick too, until a genuinely new selection is made.
- Clicking a chart bar now actually filters the table and the export to that User-Agent, rather than only reordering the table - the active-filters chip already implied a real filter ("CHART / ..."), the underlying behavior just wasn't one yet. The chart itself stays unfiltered so other bars remain clickable afterward.
- Removed the temporary "Debug: last chart click payload" expander added while diagnosing the above.

### Donut chart

Shows the top 5 User-Agents by hit count (combined across directions - a UA appearing under both egress and ingress is summed into one slice), with everything past the top 5 folded into a single "Other (N UAs)" slice so it stays readable regardless of how long-tailed the traffic is. Center of the donut shows the total hit count for the current filter.
- Each theme got a 6-color `donut` palette (5 highlight colors + a muted tone for "Other") derived from that theme's existing accent/warn/danger colors, rather than a generic unrelated rainbow.
- Read-only for now by design - no click-to-filter yet, since that's a planned follow-up.
- Legend moved to the right of the ring (was below it) with larger color swatches (`symbolSize=170`, no stroke outline) per request.
- Donut is now clickable, both the slices and the legend entries (via Altair's `bind="legend"`, with `on="click"` set explicitly - per Altair's own docs, direct chart-click interaction is disabled by default once a legend is bound, unless `on` is set explicitly to re-enable it). Clicking either opens the inspector dialog for that User-Agent - same behavior as clicking a bar, and as clicking a table row. It does not filter the table (that was tried, reverted per request - see below). Clicking "Other (N UAs)" is a no-op - it's a synthetic rollup, not a real User-Agent, so there's no single event to open. Since the donut sums a UA's hits across both directions, the specific row shown uses the same tie-break as the bar chart: whichever direction has the higher hit count wins.

### Chart clicks: filter reverted back to dialog-only
Chart-driven table filtering (added a few revisions back in response to a different complaint) has been removed. Both the bar chart and the donut now do exactly one thing on click: open the event inspector dialog for that User-Agent, the same as clicking its row in the table. The `chart_ua` session-state concept, the "CHART / ..." entry in the active-filters chip, and the "CHART FOCUS" telemetry note are all gone along with it.

### URL field: scheme-less PAN-OS values weren't being recognized as URLs
PAN-OS's URL Filtering log field is conventionally just `<domain>/<path>` - it doesn't include an `http://`/`https://` prefix; the firewall doesn't log the scheme separately there. The Last URL tile's link, and the VirusTotal/Go button visibility, both used a strict `^https?://` check, so a populated-but-unprefixed value (the normal case) was silently treated as "not a URL": no hyperlink, no buttons, even though the field had real data. The table's own "Last URL" column cell renderer had the identical bug. Both now go through one shared `normalize_url_value()` helper: a value counts as a URL if it already has a scheme, or if it's whitespace-free with a dot in the host part before the first slash (bare domain+path); either way it gets a usable href (assuming `http://` when no scheme is present), while the *visible* text stays exactly as the log recorded it - the assumed scheme is only added to the link target, not shown to the user.

### Dialog closing, for real this time
Every previous attempt at this (pausing autorefresh, inferring a dismiss from an unexpected rerun, an autorefresh-tick check, a grace period) was working around the same root problem: Streamlit gives no direct callback for a user dismissing a dialog via click-outside/Escape/X, so detecting it was always a guess, and guesses have edge cases. The fix: `st.dialog(..., dismissible=False)` disables those native dismiss paths entirely, replaced with an explicit in-dialog "✕ Close" button whose `on_click` deterministically clears `selected_ua` and calls `st.rerun(scope="app")` (scope made explicit, not just relying on the default, since a dialog behaves like a fragment and a fragment-scoped rerun would only re-run the dialog itself rather than the outer script that decides whether to reopen it). All the inference machinery (autorefresh-tick tracking, dismissed-key memory, the grace period) was removed - it's no longer needed.

`dismissible` and `on_dismiss` were added to `st.dialog` in a 2025 Streamlit release; `requirements.txt` was bumped accordingly. Separately, a Streamlit PR titled "Close leftover dialogs on full-app rerun" (found while researching this) indicates the underlying `st.rerun()`-doesn't-reliably-close-a-dialog behavior was itself a framework-level bug fixed quite recently - if this still misbehaves after upgrading dependencies, check for a newer Streamlit release, since no amount of application-level workaround fully substitutes for that fix landing.

The Close button itself was moved to the dialog's upper right and restyled as a compact square "✕", matching the header's theme-toggle button rather than a labeled "Close" button.

### Chart-filter "reverts a moment later" bug
Root cause: AG Grid was called with `reload_data=False` unconditionally. That's the right setting for a routine autorefresh tick, where the row set is unchanged and only values within it update - it preserves the grid's own sort/scroll/selection state instead of rebuilding from scratch. But it's the wrong setting the moment the row set itself is supposed to change (a new search term, tile, or now a chart-driven filter): with `reload_data=False`, AG Grid could end up not fully applying the new, smaller row set and fall back toward what it already had rendered - which looked exactly like "filters, then a moment later reverts," and explains why clicking a different UA and then back to the original one "fixed" it (each of those *did* change the filter criteria, forcing a proper reload). `reload_data` is now computed per-run: `True` only on the run where `(tile_filter, search_query, chart_ua)` actually changed since the last render, `False` otherwise - so filter changes reload properly, and everything else keeps preserving grid state as before.

The Last URL tile's hover actions now include VT and Go alongside the existing copy button, matching the pattern already used on the IP tiles. VT points at VirusTotal's public search endpoint (`/gui/search/<url-encoded-url>`) rather than its `/gui/url/<id>` permalink scheme, since the latter requires replicating VirusTotal's own URL-identifier hashing; the search endpoint reaches the same place from a plain URL-encoded string. Go just opens the URL directly in a new tab - functionally the same as clicking the URL text itself (already a link), offered as an explicit action for consistency with the tile's other buttons.

Removed the custom AG Grid cell renderer for the "Last URL" column entirely - the table now shows it as plain text. It's not needed anyway now that a URL's own tile in the event inspector has copy/VT/Go actions.

### Settings gear replaces the separate refresh dropdown + theme button
The header's refresh-rate dropdown and theme-cycle button are gone, replaced by a single gear icon (⚙) in the same spot the theme button used to occupy. Clicking it opens an `st.popover` with a theme picker (radio buttons showing each theme's full name, e.g. "Night Ops") and the refresh-rate selector. `cycle_theme()` was replaced with `set_theme(theme_key)`, a direct setter, since a settings panel affords picking a theme by name rather than cycling through them one click at a time.

### Persistence redesigned: per-browser via URL, not a shared server file
This app runs multi-user on a shared server, which the previous `dashboard_state.json` file-based approach got wrong: one shared file next to `dashboard.py` means every visitor reads and overwrites the *same* stored values, so one person picking "suspicious" or a different theme would silently change it for everyone else on the same server. That file mechanism (`PREFS_FILE`, `load_persistent_preferences()`, `save_persistent_preferences()`) has been removed entirely.

Theme, refresh rate, tile filter, and search now all live purely in `st.query_params` - genuinely per-browser, since that's just the address bar, with zero cross-user leakage and no new dependency:
- `get_refresh_seconds()` / `set_refresh_seconds()`, `get_theme_key()` / `set_theme()`, `get_tile_filter()` / `set_tile_filter()` all read/write only query params now, falling back to fixed defaults (`config.yaml`'s refresh interval, `"night"` theme, `"all"` tile) rather than a persisted file.
- Search is now included too, via a `q` query param: seeded from the URL once per session, and written back (added/removed) only when the value actually changes, not on every render.
- **Known limitation:** this persists for as long as the browser keeps the URL around - reloading, a browser-restored tab, a bookmarked link - but does not survive typing the bare hostname fresh in a brand new tab. True "same settings no matter how you arrive" persistence would need either real per-user login or genuine browser-side storage. On that: Streamlit's own team has confirmed `components.html`'s iframe deliberately omits the `allow-same-origin` sandbox flag, meaning it cannot reach `localStorage` at all - that specific shortcut doesn't exist without a third-party package (e.g. `streamlit-local-storage`), which this app doesn't currently depend on since it couldn't be verified/tested here. *(2026-09-24: newer Streamlit versions no longer omit that flag - see "Security fix: event inspector isolation restored" below for how the inspector keeps its isolation now.)*
- Reset intentionally only touches search, tile filter, and selection state - it was already scoped this way and never touched theme or refresh rate; that behavior is unchanged, just re-confirmed now that the persistence layer under it changed.


### PAN-OS-style structured search
The search box accepts a small structured query language modeled on PAN-OS's own log filter syntax, alongside the existing plain-text substring search:
```
((addr in 10.0.0.0/8) or (addr in 172.25.0.0/16)) and ((url contains 'Mozilla') or (url contains claude))
!(action eq 'allow') and addr.dst in 172.16.0.0/12
```
- **Fields** (deliberately limited to ones that map to a real table column - see `SEARCH_FIELD_MAP`): `user_agent` → User-Agent, `url` → Last URL, `action` → Last Action, `addr.src` → Last Src IP, `addr.dst` → Last Dst IP, `addr` → matches either Last Src IP or Last Dst IP (PAN-OS's own "src or dest" shorthand). First Seen, Last Seen, Direction, and Hit Count are intentionally left out - sorting, the filter tiles, and the grid's own numeric column filter already cover those, and none of them have a clean PAN-OS filter-field equivalent worth inventing one for.
- **Operators**: `eq`, `neq`, `contains` for the text fields; `eq`, `neq`, `in` (CIDR) for the IP fields (including `addr`).
- **Boolean logic**: `and`, `or`, `not`, parentheses for grouping - nested to any depth, e.g. `((a) or (b)) and ((c) or (d))` - and `!` directly before a parenthesized (or bare) expression as an exact equivalent to `not`: `!(user_agent eq 'Mozilla')` behaves identically to `user_agent neq 'Mozilla'`.
- **Bare vs. quoted values**: a value can be bare (`claude`, `10.200.36.70`) or quoted (`'Mozilla/5.0'`) - quoting is only actually required when a value contains whitespace or punctuation that isn't part of a bare word/dotted-identifier character class (a `/` in a UA string, for instance - `curl/8.0` needs to be `'curl/8.0'`), or when it collides with a reserved word (`and`, `or`, `not`, `eq`, `neq`, `contains`, `in`). *(Loosened 2026-09-24 - bare values may now contain `/`, `-`, or start with a digit; see "Fix: query tokenizer" below.)*
- **Hybrid queries**: structured syntax can be followed by trailing free text, e.g. `(user_agent contains 'Mozilla') 10.200.36.70` - the structured part parses normally, and whatever's left over gets ANDed in as an ordinary substring match across every column. `parse_pan_style_query()` decides this by parsing as much valid structured syntax as possible from the start; if tokens remain and the next one *doesn't* look like a broken continuation (another `and`/`or`/`not`, or a stray closing paren - those suggest a typo, not intentional trailing text), the leftover becomes the free-text clause. If it does look like a broken continuation, or the string doesn't start with valid structured syntax at all, the whole thing falls back to a full plain-text search instead of guessing.
- **Fallback behavior**: `parse_pan_style_query()` returns a clean success/failure/leftover triple rather than raising - on any outright parse failure (an unrecognized field, a bad operator for that field's type, unbalanced parens, a genuinely broken continuation, or just plain text like `curl`), `apply_search_query()` silently falls back to the original search-every-column substring match. This is deliberate: the query reruns on every autorefresh tick and is often typed one character at a time, so treating a not-yet-valid partial query as an error would flash red on every keystroke instead of just not matching yet.
- The active-filters chip distinguishes the two modes: `QUERY / ...` for a successfully parsed structured filter (hybrid queries count as this too), `SEARCH / ...` for the plain substring fallback.
- Implementation is a straightforward hand-written recursive-descent parser (tokenizer with per-token character offsets → AST → per-row evaluator via `df.apply(..., axis=1)`), not a regex hack - correctness (especially CIDR matching, via the stdlib `ipaddress` module) mattered more here than performance, and row counts in this dashboard (unique User-Agents, not raw log lines) are small enough that this isn't a bottleneck.


### Suspicious tile is now an independent toggle, not part of the direction group
Previously all four metric tiles (Unique UAs, Egress, Ingress, Suspicious) were mutually exclusive - clicking Suspicious replaced whatever direction filter was active, and vice versa. Suspicious is a different kind of filter (a signature match, not a direction), and there's no reason it shouldn't combine with either direction - "suspicious egress traffic" is a perfectly normal thing to want to see.
- All/Egress/Ingress remain a mutually exclusive group (`tile_filter`, one of `"all"`/`"egress"`/`"ingress"`), driven by `set_tile_filter()`.
- Suspicious is now its own boolean (`suspicious_only` in session state, `susp` query param), toggled independently by `toggle_suspicious_filter()` and ANDed onto whatever the direction filter currently is, rather than being an `elif` alternative to it.
- The export filename, the active-filters chip, and the grid's reload-on-filter-change signature (`filter_signature`) were all updated to reflect both being independently active at once (e.g. `user_agents_egress_suspicious_...csv`, chips showing both `TILE / egress` and `TILE / suspicious`).
- Reset still clears both back to their defaults (`tile_filter="all"`, `suspicious_only=False`).

### Filter chip simplified, Reset disabled when nothing's filtered
The active-filters chip no longer lists `TILE / egress`, `TILE / suspicious`, etc. - the tiles already show their own pressed/active state, so repeating that in text was pure redundancy. What the chip now shows is only whether the search box's content parsed as a structured `QUERY` or fell back to plain `SEARCH` - that's the one piece of information not visible anywhere else (a typo'd field name silently becomes a literal substring search across every column, and without some signal there'd be no way to notice). The Reset button is now disabled whenever no tile, toggle, or search is active, giving an at-a-glance "is anything filtered right now?" signal in place of what the verbose chip used to communicate.

### Settings: centered dialog instead of a dropdown popover
The gear button now opens `st.dialog(..., width="small", dismissible=False)` - a true centered modal - rather than `st.popover`, which anchored as a dropdown near the button. It uses the same reliable pattern as the event inspector dialog: a session-state flag (`show_settings_dialog`) that's only set by the gear button and only cleared by an explicit in-dialog "✕" Close button (`st.rerun(scope="app")` afterward), rather than depending on the dialog's native dismiss - which, per everything learned building the event inspector, Streamlit gives no reliable callback for.

### Play/Pause autorefresh toggle
A second square icon button sits beside the gear, styled to match. Shows ⏸ (two lines) while refreshing normally - clicking pauses; shows ▶ (play triangle) while paused - clicking resumes. This is a plain, independent on/off switch (`st.session_state.autorefresh_paused`, checked once right before the `st_autorefresh(...)` call) with no bearing on dialog open/closed state - safe to add now specifically *because* both dialogs stopped depending on autorefresh-tick inference when they moved to `dismissible=False` + explicit Close buttons. An earlier revision of this dashboard tried pausing autorefresh while a dialog was open and hit real race conditions from that coupling; this pause is deliberately decoupled from dialog state entirely, so those issues don't apply here. It's session-only (no query-param persistence) by design - a momentary "let me pause this while I look at something" state shouldn't persist as a forgotten setting across a fresh visit.

### The search box now IS the filter indicator - chip removed entirely
The awkward gap where the chip used to sit (empty when nothing was active) and the truncation problem on longer queries are both gone, because the thing causing them is gone: there's no more separate chip. The search box itself now shows exactly what's filtered, since the tiles edit its text directly.

**The core idea:** `suspicious`, `egress`, and `ingress` are new standalone predicate keywords in the query language - complete clauses with no operator or value, e.g. `(suspicious)`, unlike every other field in `SEARCH_FIELD_MAP`. They only take on this special meaning where a field name is expected (clause-start position) - `user_agent eq suspicious` still searches for a UA literally containing that word, since that's a bare value, not a field.

- **Tile click → edits the query text.** `sync_query_predicate(name, mutually_exclusive_with=None)` re-parses whatever's currently in the box, adds or removes the predicate from the parsed tree (`ast_add_predicate` / `ast_strip_predicate`), then regenerates the text (`ast_to_query_text`) and writes it back via `set_search_query()`. Egress/Ingress pass each other as `mutually_exclusive_with` so clicking one strips the other first. The "All" tile isn't a toggle - `clear_direction_predicates()` always strips both egress and ingress, leaving Suspicious and anything else in the box untouched.
- **Typing in the box → tiles reflect it.** The current query is parsed once per render (right where the tiles are built); `ast_contains_predicate(ast, name)` walks the tree to decide whether each tile shows pressed. If the query doesn't parse (mid-edit, or plain text), the tiles simply don't light up from it - no flicker, no error, consistent with how the parser already treats an invalid/incomplete query.
- **Hybrid-safe.** If the box has manually-typed free text (or something that doesn't parse) when a tile is clicked, that text is preserved as a trailing free-text clause and the predicate is added as a fresh structured prefix - e.g. clicking Suspicious with `curl` already typed produces `(suspicious) curl`, using the same hybrid mechanism the query language already supports for manually-typed queries.
- **Regenerated text is always fully parenthesized**, even for a flat chain a human might type more tersely (`(suspicious) and (egress)` might come back as `((suspicious) and (egress))` after a tile edit) - `ast_to_query_text()` always wraps `and`/`or` results in an extra parens layer specifically to guarantee correct precedence round-tripping in every case (an `or` nested under `and`, either nested under `not`, etc.) without needing to reason case-by-case about when it's actually safe to omit them. Values are always emitted quoted for the same reason - safety over terseness. The parser already accepts arbitrarily nested/redundant parens without complaint, so this costs nothing functionally.
- **Known limitation, accepted deliberately:** a tile's pressed state means "this predicate appears somewhere in the query", not "this predicate is logically guaranteed for every matching row." A hand-written `(suspicious) or (egress)` would show the Suspicious tile pressed even though a row could match via the OR without actually being suspicious. Real logical analysis to rule that out is a lot of complexity for an edge case that only shows up in hand-written OR queries.
- Direction/suspicious filtering no longer has its own separate code path at all - `tile_filter`, `suspicious_only`, `get_tile_filter()`, `set_tile_filter()`, `get_suspicious_toggle()`, `toggle_suspicious_filter()` are all gone. Every filter (including what used to be tile-driven) now flows through `apply_search_query()` alone, since it all lives in the query text. This also means direction/suspicious state persists via the existing `q` query param automatically, with no separate persistence code needed for it anymore.
- Reset's disabled state simplified accordingly: disabled whenever the search box is empty, since that's now the single source of truth for "is anything filtered."

### Multi-firewall support (Panorama-style)
Telemetry is now tracked per reporting firewall, not just per User-Agent/direction, with a device selector at the top of the dashboard: pick a specific firewall by hostname to see just its traffic, or leave it on "All Firewalls" for fleet-wide aggregated totals.

**Firewalls are never manually defined anywhere.** Every PAN-OS URL Filtering syslog already self-identifies its sending device - Serial Number (field 2) and Device Name (field 59) - so `palo_ua_tracker.py` discovers firewalls automatically as they send traffic, the same way Panorama does. `config.yaml` gained two new `log_format` indexes (`device_serial_index: 2`, `device_name_index: 59`) but no firewall list; the existing `zones` section stays global/fleet-wide, applied the same way to every device's logs (a future revision could make that per-firewall too, if different sites use different zone names for the same role).

- **Schema**: the `user_agents` table's primary key changed from `(user_agent, direction)` to `(user_agent, direction, device_serial)`, plus new `device_serial` and `device_name` columns. **This requires a fresh database** - `ALTER TABLE ADD COLUMN` can add the new columns to an old database, but SQLite can't change an existing table's primary key in place, so a pre-multi-firewall `user_agents.db` needs to be deleted (or moved aside) once before running this version, and will rebuild itself from scratch as new syslogs arrive. This was an explicit, agreed tradeoff - no migration of historical hit counts/timestamps from the old schema.
- **Ingestion (`palo_ua_tracker.py`)**: `process_syslog()` now extracts `device_serial`/`device_name` from every log and includes them in the upsert key. `device_serial` falls back to `"unknown"` only for logs missing the field entirely (bucketing any such logs together rather than dropping them); `device_name` falls back to the serial when the hostname field is blank. Because the key now includes the device, the "first time this UA/direction was seen" alert (Google Chat webhook) fires again per-device - deliberately: "this UA just showed up on a NEW firewall" is meaningful fleet visibility on its own, not a duplicate of an earlier alert from a different device.
- **Dashboard (`dashboard.py`)**: `load_devices()` lists every `device_serial` seen in the database, paired with its most recently reported `device_name` (so a hostname rename shows up as soon as new traffic arrives - no separate device-registry table needed). The firewall selector persists the chosen `device_serial` (stable across renames) in `st.query_params["device"]`, the same per-browser mechanism theme/refresh/search already use, and displays it by hostname.
- **`load_data(device_serial=None)`** now branches three ways: scoped to one device (a plain `WHERE device_serial = ?` - the row shape is already unique per UA/direction there), fleet-wide "All" (a `ROW_NUMBER() OVER (PARTITION BY user_agent, direction ORDER BY last_seen DESC)` window query: `Hit Count` is `SUM()`'d across every device that's seen that UA/direction, `First Seen`/`Last Seen` span the earliest/latest any device saw it, and every other detail field - action, URL, IPs, device identity, raw payload - comes from whichever single device most recently reported that exact pair), or the plain pre-multi-firewall query as a fallback if a database somehow still lacks the device columns. This was the one significant design decision in this feature (**Option 2**, confirmed): aggregate the totals fleet-wide, but don't try to merge per-device detail fields - show one device's worth of investigation detail, from whoever saw it most recently.
- Metrics, the bar/donut chart, the table, export, and search are all automatically scoped by whichever `df` `load_data()` returned - no separate device-filtering logic needed anywhere else, since device scope is applied once at the data-loading layer.
- New table column **Firewall** (Device Name), and new event-inspector tiles **Firewall** / **Serial Number**, placed right after Action/Direction - "which firewall enforced this" reads naturally right after "what happened," before drilling into rule/category detail. In "All Firewalls" scope these reflect the same "latest reporting device" rule as every other detail tile.
- New search fields: `device` (hostname, text match) and `device.serial`, following the same `SEARCH_FIELD_MAP` pattern as everything else - e.g. `(device contains 'branch') and (suspicious)`.
- Export filename picks up the selected firewall's hostname as a slug when one is chosen (not "All Firewalls"), e.g. `user_agents_fw-branch-1_suspicious_20260918_1200.csv`.
- The firewall selector moved onto the same row as the search bar (to its left) shortly after this shipped, once it was clear the row had room - see "Firewall selector moved onto the search row" below.

### Firewall selector moved onto the search row
Originally its own row below the header, now the leftmost control on the "Firewall / Filter / Search" row (`device_col, search_col, export_col, reset_col = st.columns([2.0, 5.5, 0.85, 0.85], ...)`). The *resolution* of which device is selected (reading/validating `device_serial` from `st.query_params`, needed by `load_data()`) still happens early, right after the header - only the dropdown *widget* itself moved down; they read/write the same `selected_device_serial` state either way.

### Zone-to-direction mapping simplified: external-only, no internal or DMZ list needed
`config.yaml`'s `zones` section no longer has an `internal_zones` list. `determine_direction()` now classifies a zone as internal purely by *not* appearing in `external_zones` - there's nothing else to maintain. This was a deliberate design discussion (see git history / conversation), not an incidental simplification:

- **The problem**: across a real multi-firewall fleet, internal zone *naming* is what varies site-to-site (`LAN`, `Users`, `Corp`, `Inside-Trust`, `VLAN10`, ...), while external/edge zone naming is typically a small, stable, centrally-controlled set (1-3 names, even fleet-wide). Requiring both lists to be exhaustively correct meant any zone name missing from either one caused that firewall's traffic to be silently dropped - no error, no trace, just absent from the dashboard.
- **The fix**: only `external_zones` is defined. A zone not in that list is implicitly "inside" - no second list to keep in sync as new firewalls (with their own internal zone-naming conventions) come online.
- **DMZ zones handled for free, no separate `dmz_zones` list**: a DMZ/partner/semi-trusted zone is simply never in `external_zones`, so under the plain "external vs. everything else" binary split, `DMZ -> external_zones` already classifies as **egress** (a DMZ host talking out - worth catching) and `external_zones -> DMZ` as **ingress** (inbound to a DMZ-hosted service - typically the most security-relevant ingress traffic there is), while `DMZ <-> internal` traffic lands in neither rule (both sides non-external) and stays unclassified, same as it always has been. An earlier draft of this feature added an explicit `dmz_zones` config list to handle this - it turned out to have zero behavioral effect over the plain external-only model and was removed before shipping, once traced through the actual classification logic case by case.
- **Explicitly ruled out**: per-firewall zone config (keyed by device serial), for fleets where a zone plays a genuinely *different role* at different sites (not just a different name for the same role). Confirmed not needed here - the inconsistency across this fleet is naming only, every firewall has the same zone topology - so the global external-only list fully solves it without the ongoing maintenance burden a per-firewall override would add (which would also cut against the auto-discovery, no-manual-config approach the multi-firewall feature itself relies on).
- Verified against a table of src-zone/dst-zone pairs (internal→external, external→internal, DMZ→external, external→DMZ, internal→DMZ, DMZ→internal, internal→internal, external→external, and a never-before-seen zone name) before shipping - every case classified as intended.

### Settings now survive closing the tab entirely (browser cookie backstop)
Query params (the URL) were always genuinely per-browser with no cross-user leakage, but they never survived closing the tab and opening a fresh one - a blank URL has no params, so theme/refresh/firewall/search all silently reset. A single browser cookie (`ua_intel_prefs`, via the `streamlit_cookies_controller` package) is now the durable backstop: on a cold load with an empty URL, `_bootstrap_prefs_from_cookie()` seeds `st.query_params` from whatever was last saved, before anything else reads them; every setter (`set_theme`, `set_refresh_seconds`, `set_search_query`, `set_selected_device`, `reset_filters`, and the search box's own inline sync) calls `_save_prefs_cookie()` afterward to keep the cookie in sync going forward. Query params remain the moment-to-moment source of truth (still what every getter reads, still what makes a link shareable with a specific view baked in) - the cookie only ever fills in a genuinely blank URL, never overrides one that already has state in it.

The cookie component needs one round trip to the browser before it can report a cookie's value back to Python, so an empty result on the very first run of a session is ambiguous (no cookie yet, vs. hasn't loaded yet) - `_bootstrap_prefs_from_cookie()` handles this with a single silent `st.rerun()` on that first run, guarded so it can't loop if there's genuinely no cookie to find. This dependency and its browser-side timing couldn't be exercised against a live browser in the environment this was built in - worth a first-run check after deploying.

### Play/Pause icon sometimes not updating on click
Root cause: `icon = "▶" if paused else "⏸"` was computed from `st.session_state.autorefresh_paused` at the top of the run, then `st.button(icon, ...)` drew the button with that (pre-click) icon; the click itself is only detected further down, when the `if st.button(...):` block runs and toggles the state - but Streamlit doesn't re-render the same widget a second time within one run, so the button already showed the stale icon for that run. Normally the next periodic autorefresh tick would trigger a rerun and self-correct within a few seconds - except clicking Pause is exactly the click that stops those periodic reruns, so without an explicit rerun the icon could stay stuck on its old state until some unrelated interaction happened to trigger one. Fixed with an explicit `st.rerun()` right after the toggle.

### Cookie warmup retried only once; play/pause still raced after that
Both of the above fixes reduced but didn't fully close their respective bugs, confirmed by continued reports after they shipped:

- **Cookie warmup**: `_cookie_warmup_done` was a one-shot flag - exactly one retry `st.rerun()`, then `_bootstrap_prefs_from_cookie()` gave up for the rest of the session even if the cookie component's browser round-trip (mount the iframe, run its JS, read `document.cookie`, post the value back over the websocket) simply hadn't finished yet. On a genuinely cold page load - the whole Streamlit frontend bootstrapping, not just this one component - one rerun isn't reliably enough time. That produces exactly "sometimes it remembers, sometimes it doesn't," purely depending on how fast the round trip happened to complete that particular visit, which is what got reported. Fixed by replacing the one-shot flag with a bounded attempt counter (`_COOKIE_WARMUP_MAX_ATTEMPTS = 3`) - still can't loop forever on a session with genuinely no cookie, but gives the component several chances to actually finish mounting before giving up.
- **Play/pause**: the explicit `st.rerun()` fix above closed the "button click alone" case but not a race with the periodic autorefresh timer's own independent rerun trigger - and pausing is exactly the click most likely to land near one of those ticks. Converted to `on_click=toggle_autorefresh` (a plain callback, same pattern already used everywhere else in this app for stateful buttons - `reset_filters`, `sync_query_predicate`, the metric tiles). Streamlit runs a callback for whichever triggering event wins BEFORE the script body executes top-to-bottom on that run, so `icon = ...` always sees the already-toggled value - no manual rerun, no window for another concurrent trigger to interleave.

### Manual refresh button
A third icon button (⟳) next to Play/Pause and Settings, `on_click=manual_refresh` clearing `load_data()`'s and `load_devices()`'s `@st.cache_data` caches so the click actually re-queries the database rather than replaying whatever was cached from up to 5 seconds ago. ### Security review: IP lookup moved off plaintext HTTP, Google Chat alerts sanitized
A pass looking specifically for SQL injection, RCE, and XSS found neither - every SQL query is parameterized or built from fixed literals, there's no `eval`/`exec`/`subprocess`/`pickle` anywhere, and every value rendered into the event inspector's HTML tiles goes through `html.escape()`, including inside `href`/`data-*` attributes. Two real issues did turn up and are fixed:

- **`lookup_ip_country()` now uses `https://ipwho.is`, not `http://ip-api.com`.** The IP lookup sends every public source/destination IP an analyst inspects to a third-party service - `ip-api.com`'s free tier is HTTP-only (HTTPS is a paid feature), so that IOC was visible in plaintext to anyone on the network path. `ipwho.is` offers the same no-API-key JSON lookup over HTTPS.
- **Google Chat alerts now sanitize `user_agent`/`device_name`/`action`/the IPs before building the message.** These all come straight from the UDP syslog listener, which is unauthenticated by design (PAN-OS syslog has no built-in auth) - a crafted packet could previously embed Google Chat's own markup (`*bold*`, `<url|label>` links) into an alert, altering its formatting or planting a misleading clickable link inside what looks like this app's own notification. `sanitize_for_chat()` swaps those trigger characters for inert lookalikes rather than stripping them, so the alert stays readable and still shows what was actually received.

**Noted but left as deployment guidance, not code changes**: the dashboard itself has no login - PAN-OS syslog carries no source authentication of its own, so this is a defense-in-depth measure, not a substitute for restricting the listener's exposure at the network level too. Put the dashboard behind a reverse proxy with auth if it's ever reachable beyond a fully trusted host.

### UDP syslog listener: source-IP allow-list
`config.yaml`'s `network` section gained `allowed_sources`, a list of individual IPs (`"10.0.0.5"`) and/or CIDR ranges (`"10.0.0.0/24"`) - a packet whose source IP doesn't match any entry is dropped before any CSV/regex parsing happens (`is_source_allowed()`, checked first thing in `main()`'s receive loop) and logged at WARNING level. Default is `["0.0.0.0/0"]` - every source trusted, matching this app's behavior before this setting existed - since the app has no way to know your firewalls' real IPs for you; narrowing this to your actual firewalls (or their subnet) is what actually closes the "anyone who can reach this port can inject fabricated telemetry" gap noted above, the allow-list is just what makes that possible to configure.

`build_acl()` parses the list once at startup (`ipaddress.ip_network(..., strict=False)`, so a bare IP is treated as a /32); an entry that fails to parse is logged and skipped rather than crashing startup over a config typo. If every entry turns out invalid (or the list is empty/missing), that would silently drop all real firewall traffic with no obvious cause - worse than the permissive default it replaced - so that specific case logs loudly and falls back to `0.0.0.0/0` rather than failing closed and silent.

### Two deprecation warnings fixed
Both surfaced from a live run against a newer Streamlit/streamlit-aggrid install than this app had been tested against:
- **`use_container_width=True` → `width="stretch"`** across every button/chart call (10 sites) - Streamlit is removing the old parameter; the newer `width` parameter is what it now points to.
- **AG Grid's `reload_data` parameter is now a silent no-op** in current `streamlit-aggrid` releases ("DeprecationWarning: The 'reload_data' parameter has been removed and has no effect"). This app relied on it to force a real table reload exactly when a search/tile/device filter changed (fixing an earlier "table filters, then a moment later reverts" bug) while preserving AG Grid's own sort/scroll/selection state on routine autorefresh ticks otherwise. Replaced with a mechanism that doesn't depend on that parameter at all: the filter signature (search text + selected device, hashed) is now folded directly into the grid's `key`, so a filter change always mounts a genuinely fresh grid component (Streamlit's own guarantee for a changed key) while an unchanged filter keeps the same key and its preserved state - same fix, no longer dependent on an AG Grid parameter that can be silently deprecated out from under it again.

### Dashboard access allow-list
`config.yaml`'s `dashboard` section gained `allowed_sources`, in the same individual-IP/CIDR format as `network.allowed_sources`. A browser whose IP isn't on the list gets a plain "Access Denied" page and nothing else - no telemetry, no UI - checked as the very first thing the script does (`_check_dashboard_acl()`, called right after `st.set_page_config()`). Default is `["0.0.0.0/0"]`, matching this app's behavior before this setting existed.

Worth reading before relying on this one: it's built on `st.context.ip_address`, which Streamlit's own docs describe as "should not be used for security measures because it can easily be spoofed." In this app's default setup - Streamlit reached directly, no reverse proxy in front - that's the genuine TCP peer address and this is an effective gate. If a reverse proxy is ever added in front of the dashboard (including for HTTPS termination, which Streamlit's own docs actually recommend over the `https.enabled` option above), every connection will appear to come from the proxy's own IP and this allow-list will silently stop doing anything useful. Treat it as a convenience gate for a direct, unproxied deployment; a host firewall/ACL in front of the dashboard's port is the real, unspoofable version of this control, and localhost connections (which report no IP at all) are always allowed regardless of the configured list.

There was no automated testing before this - verification was manual or ad hoc scripts (the zone table above, for instance, was "verified against a table of src-zone/dst-zone pairs" by hand). `tests/` is now a pytest suite of ~300 tests, run with `python -m pytest`; see [Development](README.md#development) for what it covers. Two choices worth explaining:

### 2026-09-24 — Fix: duplicate "new User-Agent" alerts

### 2026-09-24 — Known issues found by the test suite (not yet fixed)
*All four were fixed later the same day - see the three entries after this one. Kept as written for the record.*

Recorded here, and as strict `xfail` tests where they're testable, rather than fixed in passing - each one changes documented behavior, so each deserves its own decision:

- **Bare values starting with a digit don't tokenize.** `device.serial eq 013101001234` fails to parse and falls back to a plain-text search for the whole string, matching nothing. PAN-OS serials are all digits, so the documented `device.serial` field currently only works quoted (`device.serial eq '013101001234'`).
- **Hybrid trailing text only works if it tokenizes.** `(egress) fw-branch`, `(egress) 10.1.2`, and `(suspicious) curl/8` fail completely (`-`, a partial IP, and `/` aren't tokens), so the whole query falls back to a literal substring search and matches nothing. The tiles hit this too: typing `curl/8` and then clicking Suspicious produces `(suspicious) curl/8`, which empties the table. Both this and the previous item come from `_tokenize_query()` raising on anything outside its token set. A likely fix is a catch-all "bare text" token, which would also make quoting optional for values like `curl/8.0` - a grammar change, so it's left for a deliberate decision.
- **`?q=` is occasionally dropped on a browser's very first load.** Seen intermittently in a fresh headless Chrome profile, in both this version and the pre-split `dashboard.py` (so not a regression): the whole query string is cleared and the dashboard opens unfiltered, meaning a shared `?q=` link can sometimes open unfiltered in a new browser. Most likely a race between the first-load cookie bootstrap's rerun and Streamlit's query-param sync. Not reproducible on demand, so no test yet.
- **`st.components.v1.html` is deprecated.** Streamlit now warns it's scheduled for removal in favor of `st.iframe`. The event inspector's tiles render through it, and its sandboxing is part of the inspector's security story (see the `components.html` notes above), so migrating deserves its own look at the new API's sandbox behavior rather than a mechanical swap.

### 2026-09-24 — Fix: query tokenizer rejected bare values with digits or punctuation
`_tokenize_query()` only knew quoted strings, IPv4/CIDR shapes, and identifier-like words, and raised on anything else - failing the *whole* query, which then fell back to a literal substring search for the entire string and matched nothing. So `device.serial eq 013101001234` (PAN-OS serials are all digits) matched nothing, and so did hybrid queries with punctuated trailing text like `(egress) fw-branch` or `(suspicious) curl/8` - including the ones the tiles build: typing `curl/8` and then clicking Suspicious used to empty the table.

Any run of characters up to whitespace or a paren is now a single token, classified as a CIDR, a word, or a new catch-all `BARE` kind. `BARE` is accepted anywhere a value is, and as trailing free text, but never as a field name - so a plain-text search like `curl/8` still falls back to searching every column, exactly as before. The user-visible change is that quoting is now only required for a value containing whitespace or parentheses, starting with `'` or `!`, or equal to `and`/`or`/`not`: `user_agent eq curl/8.0` and `device.serial eq 013101001234` work bare. Every query that parsed before parses identically; the structured-vs-fallback rules for broken queries (dangling `and`, stray `)`, unknown field, unterminated quote) are unchanged, and tests pin both. The search box's help text says the same.

### 2026-09-24 — Fix: `?q=` dropped on a browser's first load
A shared link like `?q=(suspicious)` opened unfiltered in a fresh browser most of the time. Instrumenting the script found the cause: on a first load, the cookie component's initial mount triggers a rerun that interrupts the first script run. That first run has already seeded `st.session_state.search_query` from `?q=`, but hasn't yet reached the search box further down. A value set in a run that never created its widget isn't pushed to the browser as a new value when the widget *is* created on the next run, so the browser started the box at its `""` default and sent `""` back on the following rerun. The "keep the URL in sync with the box" code then saw an empty box and removed `q`. (It wasn't a regression from the package split - the pre-split `dashboard.py` did exactly the same.)

The fix re-assigns `search_query` to itself immediately before `st.text_input(...)` until the widget has rendered once, so the assignment happens in the same run that creates the widget and Streamlit sends it as a genuinely new value. Measured with repeated first loads in fresh headless-Chrome profiles: `q` survived 2 of 8 loads before, and 8 of 8 after. Typing, clearing the box by hand, the tiles, and Reset all still update the URL as before. The race depends on real browser timing, which Streamlit's `AppTest` can't reproduce, so the automated test only covers `?q=` seeding the box, and the before/after measurement is recorded here.

### 2026-09-24 — Security fix: event inspector isolation restored (`st.iframe` + `data:` URL)
The event inspector's tiles render every attacker-reachable syslog field, so on top of `html.escape()` on every value, they've always run in a separate iframe document. The persistence notes above describe that iframe as omitting the `allow-same-origin` sandbox flag. **On the Streamlit versions this app now installs, that stopped being true**: `st.components.v1.html` is deprecated, and it's now rendered through `st.iframe`, which embeds an HTML string with `allow-scripts` *and* `allow-same-origin`. Measured with the original code on Streamlit 1.63: script inside the inspector iframe could read the parent page's DOM and `document.cookie` (including Streamlit's `_streamlit_xsrf` token). There was no exploitable bug - the escaping held, and the tests check it - but the isolation layer the docs promise had silently disappeared, so a single future escaping mistake would have meant script running with full access to the dashboard.

The inspector now uses `st.iframe` directly, which also clears the deprecation, but hands it the document as a base64 `data:` URL (`sentry_ua.ui_helpers.isolated_iframe_src()`), never as an HTML string. A `data:` document gets an opaque origin, so it's cross-origin to the app no matter what sandbox flags Streamlit applies. Verified from inside the frame in headless Chrome: its origin is `null`, and reaching `parent.document`, `document.cookie`, and `localStorage` all throw `SecurityError`, while from the parent side `contentDocument` is `null`. All 15 tiles, the URL link, and the VirusTotal/AbuseIPDB/Go links still work (Go opens a new tab). Tests assert the inspector is a `data:` URL, never inline HTML, and push a hostile User-Agent and URL through the whole pipeline - collector, database, dashboard, iframe - to check they arrive escaped.

One knock-on fix: a `data:` document isn't a secure context, so `navigator.clipboard` doesn't exist inside it. The copy button called it unconditionally, which threw before the old `.catch()` fallback could run, so copy silently did nothing. `copyValue()` now feature-checks the Clipboard API and falls back to `execCommand('copy')`, which still works on a real click. It shows ✓ only when the copy actually succeeded (✗ otherwise). Verified with a real click in headless Chrome: the clipboard held the tile's value. `requirements.txt` now requires `streamlit>=1.56`, the first release with `st.iframe`.

### 2026-09-24 — AG Grid row selection moved to AG Grid's current API
`GridOptionsBuilder.configure_selection()` emits the deprecated string form of `rowSelection` (`"single"`) plus five legacy flags (`suppressRowClickSelection`, `rowMultiSelectWithClick`, `suppressRowDeselection`, `groupSelectsChildren`, `groupSelectsFiltered`). The bundled AG Grid 34 logs a deprecation warning for each, and they're slated for removal - the same kind of silent breakage `components.html` turned out to be. The grid now sets `rowSelection` to the object form directly (`{"mode": "singleRow", "checkboxes": False, "enableClickSelection": True}`): one row at a time, selected by clicking, no checkbox column - the same behavior as before. The `flex` values on the User-Agent and Last URL columns were removed too: AG Grid ignores `flex` when `autoSizeStrategy` is set (which streamlit-aggrid always sets) and warns about it. A screenshot of the table before and after the change is pixel-identical.

Not fixable from this app: streamlit-aggrid's own frontend re-sends AG Grid's full table of option defaults, legacy selection flags included, whenever the grid re-renders, so some deprecation and "initial property can't be updated" warnings still show in the browser console after the first rerun. They come from the wrapper, not from this app's options (a fresh page load logs none), and 1.2.1.post2 is still the latest release. Worth re-checking whenever Dependabot proposes a new streamlit-aggrid.

### 2026-09-24 — Fix: preferences cookie expired after one day
`CookieController.set()` gives a cookie a one-day expiry unless told otherwise, and the app only rewrites the cookie when a preference changes. So "settings survive closing the tab entirely" quietly lapsed a day after the last change: come back two days later and the theme, refresh rate, firewall, and search were back to defaults. The cookie now gets an explicit 365-day expiry (`PREFS_COOKIE_LIFETIME`), confirmed in headless Chrome (365.0 days, `SameSite=Strict`), with a regression test.

This came out of reviewing `streamlit-cookies-controller` itself, the one small third-party package that runs code in the dashboard's page. Findings: MIT-licensed (per its GitHub repo, even though the PyPI metadata leaves the license field blank), and its frontend bundle makes no network requests of any kind - it only reads and writes `document.cookie`. Worth knowing: its `getAll()` copies every non-HttpOnly cookie visible to the dashboard's host (including Streamlit's own XSRF token) into that browser session's server-side session state. It stays in server memory and isn't sent anywhere, but it's more than this app needs.

### 2026-09-24 — Dependency bounds, Dependabot, CodeQL
Every entry in `requirements.txt` was a bare `>=`, so any future major release of Streamlit, pandas, Altair, etc. would have been picked up by the next fresh install or Docker build, untested. Each now has an upper bound at its next major version (next minor for the 0.x cookie package). A lock file was considered and left out for now: the ranges are what CI actually tests, and a lock file only covers the exact versions it pins. To keep the bounds from going stale, `.github/dependabot.yml` opens weekly update PRs for pip, the GitHub Actions used in CI, and the Docker base image, and each PR runs full CI before it can merge. `.github/workflows/codeql.yml` adds GitHub's CodeQL scanning (the `security-extended` query suite) for the Python code and the workflows, on every push and PR plus weekly.

### 2026-09-25 — On GitHub; first CI run; Dependabot tuned
The repository now lives at `eqvsec/sentry-ua` (private until the public launch). The first CI run passed on every job on its first attempt: Python 3.10, 3.12, and 3.14, plus the Docker job's end-to-end check (a real UDP syslog packet reaching the database) on a Linux runner. Neither 3.10 nor the Linux Docker path could be exercised on the Windows machine this was built on. Commits use the maintainer's GitHub `noreply` address, so no personal email is exposed in the history.

Dependabot's first pip PR showed its default strategy doesn't fit a range-based `requirements.txt`: it raised every *minimum* to the latest release (`pandas>=3.0.6`, `streamlit>=1.64.0`, ...). pandas 3 requires Python 3.11+, so that would have silently dropped the Python 3.10 support CI tests for. The pip config now uses `versioning-strategy: increase-if-necessary`, which only proposes a change when a new release falls outside the allowed range (a new major version to vet), and that PR was closed. Its other first PRs were CI-tested and merged: `actions/checkout` and `actions/setup-python` moved to v7, clearing the Node 20 deprecation warnings every CI job had been printing, and the Docker base image moved from `python:3.12-slim` to `python:3.14-slim` (3.14 is also a CI test target, and the Docker job passed on it).

CodeQL is configured but skips itself while the repo is private (uploading results needs a paid plan on private repos). It starts running on its own once the repo goes public, together with branch protection and GitHub private vulnerability reporting, which are set up at that point.
